## Executive Summary & Core Dilemma

We are preparing a multi-turn Supervised Fine-Tuning (SFT) dataset for fine-tuning **Google Gemma 4 31B IT** (`google/gemma-4-31b-it-qat-w4a16-ct`) using an Unsloth Rank-8 LoRA on a single NVIDIA L4 24GB GPU. The target agent operates in an autonomous SWE-bench evaluation container where it receives an issue description, explores an unseen Python repository, edits a single `.py` file, verifies the fix, and submits a patch.

To train this agent without leaking test benchmarks (0% contamination against `tasks.jsonl`), we extract 1,500 candidate trajectories from external open datasets (`swe_smith` and `swe_zero`, termed **Source B**).

### The Fundamental Tension
Raw Source B trajectories were generated by Claude/OpenHands agents using primitive tools (`bash`, `str_replace_editor`). They contain 15–38 raw actions per task, heavily padded with unproductive Linux shell commands (`ls`, `pwd`, failed `grep`, syntax typos, and thrashing loops).

Our offline Pydantic AI translation pipeline (`pydantic/translate_sft_dag.py`) distills these 15–38 raw steps into **4–8 clean steps** strictly matching our production tool contract:
- **5 Direct Tools:** `read_file`, `edit_file`, `write_file`, `get_status`, `submit_patch`
- **5 Pre-installed Skills:** `fast-grep`, `code-map`, `code-oracle`, `repro-check`, `test-gate` (via `run_skill_script`)
- **Zero `run_command`** (forbidden by competition rules).

### The Consultant Dilemma
> **"If we scrub the raw trajectories down to concise, expert-like steps, does the model suffer from Covariate Shift / Behavioral Cloning Collapse (DAgger dilemma)? When Gemma 4 encounters an unexpected test failure, syntax error, or empty search result at runtime, will it freeze or thrash because it was only trained on distilled paths?"**

## 2. Data Cleaning: Scrubbing Noise vs. Retaining Functional Pivots

A critical distinction in our pipeline is the boundary between **destructive over-cleaning** (which causes behavioral collapse) and **syntax normalization**:

```
                       [RAW SOURCE B TRAJECTORY]
                                  │
         ┌────────────────────────┴────────────────────────┐
         ▼                                                 ▼
[UNPRODUCTIVE NOISE: SCRUBBED]                [FUNCTIONAL PIVOTS: RETAINED]
- `ls -la`, `pwd`, `echo $PATH`               - `repro-check` FAILS (AssertionError)
- Failed bash syntax / typo commands          - Multi-match `fast-grep` -> reading file A
- Redundant repeated calls (thrashing)          -> realizing wrong file -> reading file B
- Viewing irrelevant 2000-line docs           - Initial `edit_file` fails tests -> 2nd edit
                                              - Final `test-gate` PASSES -> `submit_patch`
```

### Key Clarifications for the Reviewer:
1. **Real Sandbox Observations:** Observations are not synthetic "Success!" strings. `ReconcileObservationsNode` extracts the actual sandbox outputs from the original trajectory (compiler errors, pytest tracebacks, grep matches) and pairs them with the translated actions.
2. **Negative Feedback Loops:** Trajectories in the SFT dataset contain turns where tests fail (`AssertionError: expected X got Y`). The model is conditioned to see a failing test observation and emit a corrective `read_file` or `edit_file` action rather than a premature `submit_patch`.
3. **Length Distribution:** 
   - Raw tasks in `raw_candidates_1500.jsonl`: Mean 19.4 steps, Median 19 steps, Max 38 steps.
   - Distilled tasks: 4 to 8 steps. 
   - A 20-step trajectory would generate 40 conversation turns ($\approx 5,000$ tokens), which exceeds the 3,072-token training ceiling and would be discarded by the tokenizer anyway.

## 3. Two-Tier Runtime Safety Net (Prompt Governor)

The LoRA adapter does not operate in isolation. At inference time, the agent runs against the 153-line production system prompt (`submissions/track1_live/prompts/main.md`), which enforces explicit behavioral recovery rules:

1. **Anti-Thrashing Circuit Breaker:**
   - *Rule:* If an identical tool call with identical arguments is emitted twice consecutively, the harness injects an explicit error: `"Identical repeated action rejected. Choose a different diagnostic action."*
2. **2-Strike Edit Oscillation Rule:**
   - *Rule:* If an `edit_file` fails to apply or `repro-check` fails twice consecutively, the agent is instructed to cease editing and re-read the enclosing class or function scope (`read_file`).
3. **Dynamic 4-Probe Scratchpad:**
   - *Rule:* Before generating a tool call, the model evaluates:
     1. Current Hypothesis
     2. Evidence from last tool response
     3. Next intended action
     4. Stop condition

## 4. The External Consultant's Questionnaire

*If you were an external agentic ML consultant auditing this pipeline, what information and experiments would you demand before signing off on this training approach?*

### Category A: Dataset Composition & Pivot Coverage
1. **Pivot Transition Frequency:** What exact percentage of SFT decision windows in `sft_windows.jsonl` contain negative observations (`test_failure`, `zero_search_results`, `edit_mismatch`) followed by a corrective recovery action?
   - *Risk:* If $>85\%$ of trajectories are linear happy paths ($A \to B \to C \to D$), the model will be brittle to test failures in unseen repos.
2. **Gold Patch Leakage Audit:** Does any observation or prompt in the distilled trajectory leak line numbers, commit messages, or diff hints from the gold patch that would not be available in the test-time issue description?
3. **Tool Call Distribution Balance:** Across the 1,500 tasks, what is the frequency ratio between the 5 skills and 5 direct tools? (Specifically: is `repro-check` called in at least 60% of trajectories before `edit_file`?)

### Category B: Tokenizer Alignment & Loss Dynamics
1. **Prefix-Delta Exact Match Verification:** Is `full_ids[:len(prefix_ids)] == prefix_ids` 100% verified across every generated window? If right-truncation occurs at 3,072 tokens, does the assistant completion get cut off, producing 0 loss tokens?
   - *Reference Lesson:* Standard HuggingFace right-truncation discards tail completions. Our collation pipeline uses sliding left-truncation to guarantee completion label supervision.
2. **Loss Convergence Signals:** In our 5-test cloud probe, does the training loss smoothly descend from $\sim 2.1$ to $\sim 0.6$ with non-zero gradient norms?

### Category C: Evaluation & Distribution Shift
1. **Evaluation Benchmark Drift:** How does the LoRA perform on our 5 held-out offline SWE-bench tasks versus the base model with Track 1 prompts?
   - Metric: Does tool call syntax error rate drop from $\sim 15\%$ to $<1\%$?
   - Metric: Does the agent terminate with valid patches within 15 turns instead of timing out at 40 turns?
2. **Base Model vs Adapter Responsibility:** Is Rank-8 on `q_proj`, `v_proj`, `o_proj` sufficient to steer tool formatting without damaging Gemma 4's underlying coding and logical reasoning abilities?

## 5. Consultant's Assessment & Recommendations

### Assessment
The decision to distill 20+ wandering bash steps into 4–8 structured steps is **fundamentally sound and necessary** given the `max_seq_length=3072` hardware ceiling and the declarative 5-tool + 5-skill competition contract. Training on raw Source B commands (`ls`, `echo`, `chmod`) would actively corrupt the agent's action space.

However, to prevent Behavioral Cloning Collapse, the SFT dataset must not be purely monotonic.

### Recommended Actions Before Final Leaderboard Submission
1. **Enforce a Minimum Pivot Quota in the Translator DAG:**
   - Require that at least **35% of accepted trajectories** contain an explicit verification failure step (e.g. `repro-check` returning a non-zero exit or assertion error) followed by a successful patch and verification.
2. **Ablation Probe on GCP (Track 2):**
   - Run a 100-step SFT checkpoint and evaluate on the 5 offline test instances (`scripts/test_agents_diagnostic.py`). Compare trajectory length, recovery rate after failed edits, and resolution rate against the Track 1 baseline (0.13).
3. **Continuous Checkpointing:**
   - Save intermediate checkpoints at steps 250, 500, 750, 1000 to catch any catastrophic forgetting of Python coding knowledge.
